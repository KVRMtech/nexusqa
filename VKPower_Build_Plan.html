02

The one invariant everything is built on

A RUN = Tenant · App · Environment · Member · Scenario
— executed in one fixed order, recorded during the crawl:
Environment→ Member→ Verify documents→ Home→ Flow / Scenario

Environment is always first. Verify-documents is a real stage (some members verify/sign, some skip). Home reached is the success signal — so both branches count as logged-in.

03

Six non-negotiables at this scale

1
Tenant isolation is absoluteEvery row tenant-scoped, RLS backstop, and a per-tenant encryption key. One client's secrets never share a key with another's.
2
Record once → reuse fleet-wideRecipes are shared assets keyed by login-type/domain — a handful serve hundreds of apps. This is what makes 1000+ apps possible.
3
Everything is a parameterized recipeLogin and environment are both steps + blanks. Members, boxes, runways are just values you swap.
4
Home is the truthLogin success = reaching the logged-in state, so a verify-documents branch never breaks replay.
5
Fair, self-healing runsPer-tenant fairness + admission mutex + orphan cleanup. No client starves another; no stuck "busy" locks.
6
Backup & audit are foundationsAutomated per-tenant backup/restore and tamper-evident evidence — from day one, not bolted on.

Login recorder in the crawl — incl. Verify-documents

The box/runway is a {parameter} — save presets for fixed boxes (786, 787…) or pass it at launch for spun-up-per-test. Thousands of boxes ≠ thousands of registrations.

Track C · Reuse at fleet scale
5

Recipe Library + smart reuse — the fleet lever

Store login recipes keyed by login-type/domain (“usaa.com portal login”), shared across apps & testers. Propose on onboard: “Portal login already captured — just enter your member number.” Detect dotcom vs portal.

THE lever for 1000+ apps: a few login-types serve hundreds of apps; one tester records, the fleet reuses. Kills the “1000 testers re-record” waste.

Where: Onboard/Access proposal + recipe library
New · highest leverage
6

Members & credentials at scale

Members as tenant-level entities (one member reused across a client's apps), encrypted per tenant; reservation (one live session per member — no collisions), rotation, staleness sweep, reservation cap.

With 1000+ apps running, reservation prevents session collisions; rotation/staleness keep secrets healthy.

Where: Members list + Run launcher + credential store
Partial → scale-harden
Track D · Run & operate at scale
7

Run orchestration at scale

A queue/scheduler with per-tenant fairness + concurrency limits, admission control (one-run-per-key mutex), an autoscaling runner pool, and robust run lifecycle — heartbeats, timeouts, orphan cleanup (no stuck “busy” locks).

100+ clients × 1000+ apps → many concurrent runs; fairness stops one client starving others; lifecycle keeps the fleet self-healing.

Where: orchestrator + runner pool
Partial → scale-harden
8

Governance, evidence & operate

Per-tenant RBAC, audit trail, approval workflows, PII-egress controls, posture governance (prod default-deny / no-submit), tamper-evident Certificate-of-Execution per run — plus observability (health, SLOs, per-tenant cost).

Regulated 100+ clients require per-tenant audit + evidence + cost; posture fences prod across the fleet.

Where: all services + governance/observability layer
Partial → complete for enterprise

07

Decisions — locked

Confirmed with the founder; folded into the phases above.

A1
“Members”, not “Personas” — and the identifier is generic: the login blank adapts to whatever the app uses ({member_number}, {email}, {username}, {policy_no}). Label re-skinnable per client (Members / Customers / Users); default Members.
A2
CIT boxes = both. The box/runway is a {parameter}: save named presets for fixed boxes (786, 787…), or pass the value at launch for spun-up-per-test. One recipe, filled from a preset or at run time.
A3
Verify-documents = recorded steps. Record the document-verification steps in the crawl (like login); replay them, skip when the member has none. Safety net: a document the recording doesn't cover is surfaced, not auto-clicked.
A4
Pooled cloud now, siloable per client. One multi-tenant cloud with per-tenant keys by default; Phase 1 keeps tenant boundaries clean so any regulated client can be carved into a dedicated / on-prem / per-region instance without rework.
