# GitOps Deployment Model

This directory contains the GitOps glue that drives every Kubernetes cluster
running the platform. **No deployment is performed via `kubectl apply` or
`helm upgrade` in normal operations** — every change reaches a cluster through
a Git commit that is reconciled by a GitOps controller running in that cluster.

The controller is Argo CD. Every Argo CD object in this tree is declarative
data, parameterised by environment overlays under `envs/<env>/`. No
manifest hardcodes a repo URL, a cluster name, a namespace, or an image
tag — those flow from environment values and from the cluster generator
in the ApplicationSets.

## Operator workflows

| Action | Command | What happens |
|---|---|---|
| Bootstrap a new cluster | `make bootstrap CLUSTER=<name> ENV=<env>` | Installs Argo CD + applies `bootstrap/30-root-app.yaml` into that cluster. After this, no further imperative commands. |
| Promote a release | open PR that bumps `envs/<env>/config.yaml:targetRevision` | The ApplicationSet picks up the new revision; Argo CD syncs the cluster automatically (with the env-specific sync policy). |
| Add a new environment | `cp -r envs/staging envs/<new>` + adjust `config.yaml` | The ApplicationSets generate one Application per env automatically. |
| Add a new cluster (same env) | add cluster to Argo CD's cluster registry; tag with `env=<env>` | The ApplicationSet's cluster generator emits an Application for each matching cluster. |
| Dry-run a change | `make diff ENV=<env>` | Renders the manifests Argo CD would apply and diffs against the live cluster. |

## Why ApplicationSets, not Applications

Every Application is generated from an ApplicationSet (in `applicationsets/`)
using the **cluster generator** plus a **list generator** over environments.
Adding a cluster, an environment, or a controller is a values change, not a
new file per combination. This satisfies the "no hardcoded routing rules"
architectural principle at the deployment layer.

The single static Application in `bootstrap/30-root-app.yaml` is the only
exception. It is the seed that brings everything else under management
(the "app-of-apps" entry point).

## Why AppProjects

Three projects partition the cluster's deployable surface:

| Project | What may be deployed | Where it may be deployed | Who may sync |
|---|---|---|---|
| `infra` | Approved CRDs and controllers from `bootstrap/` and `applicationsets/infra-controllers.yaml` only | `kube-system`, `cert-manager`, `external-secrets`, `linkerd*`, `argo-rollouts` | platform SRE on-call group |
| `observability` | Approved sources for `kube-prometheus-stack`, `loki`, `tempo`, `grafana` | `observability` namespace only | platform SRE on-call group |
| `platform` | Charts under `infrastructure/helm/nexus-qa/` only | `nexus-platform` namespace only | platform release engineers |

These projects are enforced by Argo CD; an Application that names a source
outside its project's allow-list cannot be created at all. This implements
the "tenant isolation by construction" principle for the deployment plane.

## Secrets

No secret value lives in this directory. ESO (External Secrets Operator)
syncs values from the cluster's bound KMS — Secrets Manager, Vault, or
Key Vault depending on cloud — into Kubernetes Secrets. The Helm chart
references those Secrets by name; the names are stable per environment
and stored in `envs/<env>/config.yaml`.

The ESO installation itself is bootstrapped by `applicationsets/infra-controllers.yaml`
(M0.2 territory). The cluster's identity (IRSA / Workload Identity /
managed identity) is the only out-of-band trust anchor; everything else
flows through Git.

### Cluster registration label `cloud`

Every cluster Secret registered in Argo CD MUST carry a `cloud` label so
the `infra-resources` ApplicationSet can pick the matching
`ClusterSecretStore` definition for that cluster:

```yaml
# argocd-cluster-<name>.yaml
apiVersion: v1
kind: Secret
metadata:
  name: cluster-prod-us-east
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
    env: production
    cloud: aws            # one of: aws | gcp | azure | vault
type: Opaque
stringData:
  name: prod-us-east
  server: https://k8s.prod-us-east.internal
  config: |
    {"bearerToken":"<>","tlsClientConfig":{"insecure":false}}
```

The `infra-resources` AppSet uses `{{cloud}}` to render the path
`infrastructure/gitops/resources/external-secrets/{{cloud}}` per cluster.
Resources under `external-secrets/common/` are deployed to every cluster
regardless of provider.

Operationally, no other label is sensitive to cloud — engine pods are
identical across providers; the storage backend, KMS binding and CSS
swap independently per cluster. See [Rotation runbook](./SECRETS_ROTATION.md)
for the end-to-end rotation lifecycle.

## Promotion model

Environments are promoted **strictly forward**: a revision that runs in
`dev` may be promoted to `staging`; a revision that runs in `staging` may
be promoted to `production`. Promotion is a PR that bumps
`envs/<env>/config.yaml:targetRevision` from `<prev>` to a new
`<commit-sha>`. Promotion never happens by direct push to `main`; the
branch protection on this directory requires review from the release
engineering rotation.

Production Application uses `syncPolicy: automated: prune: false` and
requires manual approval in the Argo CD UI for the first sync of any
new image tag. Lower environments use `automated: prune: true,
selfHeal: true`.

## What this directory does NOT do

- It does not install Argo CD itself the very first time. Bootstrap is a
  two-command procedure documented in `Makefile`. After that bootstrap,
  every subsequent Argo CD upgrade is reconciled through Argo CD itself.
- It does not store secret values. Anything secret comes from ESO.
- It does not contain Terraform / cluster provisioning. That is M0.7 and
  lives under `infrastructure/terraform/`.
